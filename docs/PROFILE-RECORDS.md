# Profile: a record array in the native CLI after Phase 8a

Where the native CLI's time goes on a large array of small records, the
shape of a user's real 26.5 MB file, now that types are inferred from
running tallies ([STREAMING-INFERENCE.md](STREAMING-INFERENCE.md)). It also
covers how fast our JSON readers are next to `serde_json` and `simd-json`,
what in them is quicktype's semantics and what is implementation overhead,
and a ranked list of changes that keep the output byte-identical.

The profile itself changed no product code: the prototypes in
[Opportunities](#opportunities-ranked) were built in a scratch copy, only
to measure their gains. Items 1, 3a, 3b and 6 have since been
implemented, measured and checked; see [Status](#status).

## Summary

- **The CLI takes 52 ms for the 26.8 MB file (about 515 MB/s) and 480 ms
  for the 267 MB one**, with 10.5 and 44 MiB peak RSS. That is 14.6× and
  11.4× faster than quicktype's TypeScript CLI (757 ms, 5.5 s; 390 MiB,
  1.4 GiB). It is 2.0× and 2.1× faster than our own reference path
  (`QUICKTYPE_INFERENCE=compressed-json`, the pre-8a path: 105 ms and
  1.02 s; 84 and 572 MiB). The output is the same in all three, for
  `--lang typescript`, `--lang rust` and `--lang typescript --just-types`.
- **95% of the run is reading the sample** (46.4 ms of 48.8 ms in
  process; 97% at 267 MB). Inference from the tallies takes 1.1 ms, all
  the graph rewrites together 0.1 ms, naming 0.76 ms, rendering 0.12 ms and
  writing 0.19 ms. Starting and ending the process takes about 3 ms. The
  language and `--just-types` make no measurable difference: the
  generated code is 13 to 226 lines.
- **Reading splits into four parts** (100k records, CPU): stream-json
  tokenizing 22–23 ms, keeping a window of the file 4.5–5.5 ms, classifying
  the strings (date, UUID, ...) 7 ms, and tallying (keys, string cases,
  counts) 11 ms. A third of the whole run is one loop: the tokenizer scans
  string bodies one byte at a time.
- **The parser is reasonable but not fast.** The stream tokenizer alone
  reads 960 MB/s from a file and 1.16 GB/s from memory. In memory,
  `serde_json` validates at 2.0 GB/s (into `IgnoredAny`) and `simd-json`
  builds its tape at 2.1 GB/s; from a file, `serde_json::from_reader` reaches
  only 450 MB/s. With the CLI's work on top, the full reader runs at
  585 MB/s.
- **Prototypes of the top three opportunities cut the CLI's time by
  38–41%**, with identical output on every input tried
  ([exactness](#exactness-of-the-prototypes)). 100k records:
  53.8 → 34.0 ms; 1M records: 488 → 287 ms. Peak RSS at 1M drops from
  43.5 to 7.5 MiB. They scan string bodies 8 bytes at a time, make the
  per-token and per-string checks cheaper, and stop counting the string
  values of a place once those can no longer change its type. Details are
  under [Opportunities](#opportunities-ranked).
- **Implemented so far: items 1, 3a, 3b and 6 make the CLI 31–32% faster
  on this input** (100k records: 52.3 → 35.9 ms; 1M: 478 → 323 ms), 15%
  faster on text-heavy records and 13% on pokedex, with identical output
  on 20,484 CLI runs against main ([Status](#status)). Items 2, 3c, 5 and
  8 are next.

## Method

**Input.** Generated by `generateRulings` in
`npm/quicktype-core/test/bench/generate.mjs` (seeded). It is a top-level
array of records
`{"object":"ruling","oracle_id":<uuid>,"source":"wotc"|"scryfall","published_at":"YYYY-MM-DD","comment":<8–37 words>}`.

| File | Records | Bytes | Distinct `oracle_id` | `comment`s of at most 64 UTF-16 units (interned, all distinct) | Escapes |
|---|---:|---:|---:|---:|---:|
| `rulings-100k.json` | 100,000 | 26,752,869 | 34,539 | 10,671 | 0 |
| `rulings-1m.json` | 1,000,000 | 267,295,024 | 350,307 | 107,412 | 0 |

Each record has 5 keys and 5 string values. The comment averages 137
characters, and comments are half the bytes. The inferred type is one
class: two enums (`Object`, `Source`), a `string` with a UUID check, a
`Date` and a plain `string`. Every run here writes the same output as
quicktype's TypeScript CLI.

**Builds.** `cargo build --profile profiling -p quickertype` (the release
profile, fat LTO and one codegen unit, plus line tables) at `250f1661f`,
with mimalloc as in the release CLI. Phase splits and allocation counts
come from a second build of the same commit in a scratch work tree. Its CLI
wraps mimalloc in a counting allocator and records wall time, process
CPU time (`CLOCK_PROCESS_CPUTIME_ID`) and allocations at each mark. The
marks are: after the options, after the samples are read (in
`make_input_data`), at every `onTiming` pass, after `quicktype_multi_file`
returns, after the output is written and after stdout is flushed. Reading
allocates only about 120 times, so the counting changes nothing there. The
in-process sum (48.8 ms) plus process start and exit (about 3 ms) matches
the plain binary's 51.9 ms.

**Timing.** A harness forks and execs the command and reads `wait4`'s
rusage: wall time, CPU time (user + system) and peak RSS. It runs one
untimed warm-up first, then 15 runs (100k records) or 7 runs (1M) for the
Rust CLI, 11 or 5 for the reference path, and 5 or 3 for Node. Tables show
medians. The input files stay in the page cache.

**Profiles.** `samply record -r 4000 --iteration-count 40` (4 for the 1M
file), with `--unstable-presymbolicate`. Samples are weighted by each
thread's CPU delta. Inline frames come from `atos -i` for every sampled
address. Flame graphs are drawn with `inferno-flamegraph` from the folded
stacks (see [Artifacts](#artifacts)). Percentages are of the CPU time of the
thread that runs quicktype. The main thread only starts that thread and
joins it.

**Parse bench.** A throwaway crate built with the same profile settings
and allocator, plus a counting wrapper. It calls the readers through hooks
added to the scratch copy of quicktype-core, and calls `serde_json` 1.0.154
and `simd-json` 0.15.1 directly. Each variant runs in its own process, for
11 iterations (100k) or 3 (1M), in two interleaved rounds. Tables show the
median CPU time of each iteration.

**TypeScript.** `node dist/index.js` of quicktype 24.0.0 at `c39af7d3`
(`tests/golden/REFERENCE`), with `--debug print-times` for its passes.
`node --cpu-prof` split the rest.

## Machine and load

- Apple M2 Max: 8 performance and 4 efficiency cores, 64 GiB.
- macOS 26.6.2, rustc 1.99.1, Node.js v24.16.0, samply 0.13.1.
- Other agents shared the machine. The tables were taken at a load average
  of 2.4 to 4 on 12 cores, interleaved, and repeated runs agree within 2–3%.
- A first run of the same matrix, at a load average of 50 to 70, was 20%
  slower in CPU time as well (61.4 instead of 50.6 ms for 100k records),
  not only in wall time. Under load the scheduler also uses the efficiency
  cores. So compare CPU times only within one table.

Besides reading, three things stand out:

- **`read input`** (1.1 ms, 11 ms at 1M). Almost all of it replays the
  `comment` field's 10,671 (107,412 at 1M) short, distinct comments into
  the union accumulator. That costs two `String` allocations per case:
  `add_string_case` copies the text into the accumulator's case map, and
  `get_member_kinds` clones the map. The result is then thrown away: the
  same place also holds long comments, which make its string type
  unrestricted, and an unrestricted type absorbs any set of cases.
- **The peak live heap at 1M** (12.2 MB after reading, 35 MB during
  inference) is those cases: their text, the case table of the place and
  the string table's index.
- **`gather names`** is not about the input. 0.7 ms and 12,600 allocations
  of it build pluralize's multi-pattern regex for the rule list once per
  process (`pluralize::singular` → `regex_automata` `build_many`). The
  array's item type name is a singular, so the regex is always built.

### What the readers do beyond parsing, and what it costs

Measured on the 100k file. Each step below adds to the step before it,
with the stream reader from a file:

| Work | Cost | Inherent to quicktype's semantics? |
|---|---:|---|
| Tokenizing with stream-json's grammar, states and error messages (`expected ','` and so on, no positions) | 22.2 ms in memory | The grammar check is. The byte-at-a-time scan is not ([item 1](#opportunities-ranked)). |
| The window over the file: 64 KiB reads, decoding like Node's `StringDecoder` (lossy UTF-8 across chunk boundaries), dropping consumed text | +4.5–5.6 ms | Reading the file is. Of the rest, the per-token discard check is about 2.3 ms, and copying and validating chunks about 2 ms. |
| Classifying string values: date, time, date-time, integer and boolean strings, UUID, URI, and the UTF-16 length for interning | +6.7–7.3 ms | Yes, for each value that can still change its place's type (see [item 2](#opportunities-ranked)). The order of the checks is not: every UUID goes through five other checks first. |
| Tallying: per-object key lookup, interning and counting short strings per place, kinds, combined attributes | +10.8 ms | The counts are, while a place can still become an enum. Hashing every case is not, and neither is counting at an unrestricted place. |
| Key order and duplicates | 0 | stream-json keeps source order and every duplicate. The only cost is one 9-byte comparison per key, with `"__proto__"`. |
| Error positions | 0 | stream-json's messages carry none. The `JSON.parse` reader re-parses with the port of V8's parser only on a syntax error, to get V8's message. |
| Number semantics | 0 here | The file has no numbers. An integer literal is compared, as a string, with the target's range. |

The `JSON.parse` reader (the WebAssembly engine's) already scans string
bodies 8 bytes at a time, with a SWAR mask (`plain_run`). That is why it
tokenizes faster (19.6 ms) despite recording a tape and replaying it in
`Object.getOwnPropertyNames` order. Its costs on top are JavaScript's key
order (array-index keys first, a duplicate key keeps its last value, one
`__proto__`), found with per-key stamps without sets, and the tape:
12 bytes per value or key, 25 MB for this file. The classification and
the tallies cost it the same as the stream reader. Into the tallies it is
7 ms slower than into `CompressedJSON` (38.6 against 31.6 ms), because
`CompressedJSON` interns each key once per key-table id, while the
tallies compare each key with the expected one and hash every short
string.

## Inherent and implementation overhead

**Inherent**, so it must stay for exact output:

- One pass over every byte that checks stream-json's grammar and reports
  its errors at the same points. The floor is a validating scanner: 13 ms
  for this file (`serde_json` into `IgnoredAny`, the `simd-json` tape),
  against 22 ms for our tokenizer in memory today.
- Classifying each string value at a place whose type a string can still
  change, and counting its distinct short strings (≤ 64 UTF-16 units) with
  their counts, which enum inference and the `$ref` check need.
- Per-object key bookkeeping for the places (counts, first-seen order,
  `__proto__` runs).
- Inference, the rewrites, naming and rendering: about 2 ms in all, and
  constant, except for the case replay described in [Phases](#phases).

**Implementation overhead**, which can go:

- Scanning string bodies one byte at a time: about 30% of the run.
- Checking whether to discard consumed text before every token: about
  2.3 ms.
- The window copies each decoded chunk and validates it. That is 2.2 ms
  more than reading from memory, even after the prototype below.
- The order of the classifier's checks for UUIDs, and measuring the
  UTF-16 length of strings far longer than 192 bytes: about 3 ms.
- Interning, counting and storing every short string at a place that is
  already unrestricted (`comment`). Then inference replays those cases
  with two allocations each, only for an unrestricted type to absorb them.
  This costs about 2 ms of reading, 1.1 ms of inference and, at 1M, 12 MB.
- Building pluralize's rule regex in every process: 0.7 ms, which is 15%
  of a small run such as pokedex (4.8 ms).
- Process start: 3 ms, of which fork and exec take 2.4 ms on this
  machine. Not worth chasing.

## Opportunities, ranked

The gains below are for the default run, `-l ts`. The CLI rows measure the
scratch prototypes inside the real CLI: the same instrumented binary,
switched by environment variables, in three interleaved rounds. Medians,
wall / CPU ms:

| Prototype | 100k records | 1M records | Peak RSS 1M |
|---|---:|---:|---:|
| none (as on main) | 53.8 / 52.4 | 488 / 486 | 43.5 MiB |
| 1 + 3: SWAR string scan, one-compare discard check, classifier fast path | 35.8 / 34.4 | 314 / 312 | 43.5 MiB |
| 2: skip strings at unrestricted places | 50.6 / 49.3 | 456 / 454 | 7.5 MiB |
| all of them | **34.0 / 32.6** | **287 / 285** | **7.5 MiB** |

That is −38% and −41%, and from 515 to about 790 MB/s end to end at 100k
records. In the parse bench, the prototype tokenizer reads 1.64 GB/s from
a file (16.3 ms) and 1.90 GB/s from memory (14.1 ms). That is within 5–15%
of `serde_json`'s validation and the `simd-json` tape. The tallies read
through it at 920 MB/s (29.2 ms, without prototype 2).

1. **Scan string bodies a word at a time in the stream tokenizer.**
   *Done; see [Status](#status).* Port
   `plain_run` from the `JSON.parse` reader to `Tokenizer::skip(is_plain)`:
   test 8 bytes with a SWAR mask for `"`, `\` and bytes below 0x20. Take
   the first stop from the mask's lowest set bit (borrows only propagate
   upward, so the lowest flagged byte is exact), and fall back to bytes
   at the end of the window, where `fill` may add more.
   - *Gain:* tokenizing in memory 23.1 → 14.1 ms; the tallies from a file
     about −11 ms per 100k records (−21% of the run). With item 3: the
     tokenizer from a file 27.6 → 16.3 ms, the CLI 52.4 → 34.4 ms of CPU
     (−34%).
   - *Exactness:* the same set of stop bytes and the same first stop, so
     every token, event and error is the same. Bytes of 0x80 and above
     stay plain, as `is_plain` has them. A NEON version (16 bytes) could
     go further. `skip_whitespace` could get the same treatment for
     pretty-printed input; here whitespace is 3.6%.
2. **Stop counting a place's strings once they cannot change it.** When a
   place's combined string attributes are unrestricted both with and
   without enum inference, nothing more is needed from its string values.
   Such a string is skipped: no classification, no interning, no count.
   Two kinds still go through. Strings that could be URIs (first byte `h`
   or `f`) do, because URI attributes (protocols, extensions) are combined
   beside the string types. Strings under a `$ref` key do too, since
   reference handling reads their cases.
   - *Gain:* −3 ms per 100k records (−6%) and −32 ms at 1M. Inference
     (`read input`) drops from 1.1 to 0.06 ms (11.2 to 0.06 ms at 1M). The
     peak live heap at 1M drops from 12.2 to 0.4 MB, and the peak RSS from
     43.5 to 7.5 MiB. Text-heavy inputs gain more: free-text fields of
     short distinct strings are where the tallies' memory goes
     ([BENCHMARKS.md](BENCHMARKS.md#streaming-inference-phase-8a)).
   - *Exactness:* `StringTypes.union` is unrestricted as soon as any
     member is, so the cases and transformations of further values cannot
     appear. `getMemberKinds` combines the cases into the unrestricted
     attributes, and `$ref` resolution reads cases only under `$ref`
     keys, which are never skipped. URI attributes still go through.
     Kinds are unaffected: strings do not enter the first-seen order of
     non-string kinds.
   - *Check:* the graph is unchanged, since no cases remain under an
     unrestricted type, and the differential harness compares exactly
     that: `{:?}` of every type with every attribute, against the
     reference path. With the prototype it found
     [no difference](#exactness-of-the-prototypes).
   - *Alternative:* a narrower version only skips the case replay in
     `TallyInference::add_values_to_accumulator` when `with_enums` is
     unrestricted. That saves the 1.1 ms of inference, but none of the
     memory.
3. **Cheaper per-token and per-string checks.** *The first two are
   done; see [Status](#status).*
   - Compare with one precomputed threshold in `discard_consumed`
     (`usize::MAX` in memory, the chunk size when streaming), instead of
     checking `reader.is_some()` and the chunk size on every token. That
     saves about 2.3 ms: the window's extra cost goes from 4.5 to 2.2 ms.
   - Try the UUID shape first (36 bytes, `-` at index 8) when the
     recognizer is the default one. Under the default recognizer a UUID
     cannot be a date, time, date-time, integer or boolean string, which
     the chain tests first. Custom recognizers keep the order.
   - In `TallyBuilder::commit_string`, add `CompressedJson`'s bound
     `s.len() <= 64 || (s.len() <= 192 && utf16::len(s) <= 64)`, which is
     exact since a UTF-16 unit takes 1 to 3 UTF-8 bytes, and 4 bytes make
     two units.
   - *Gain:* classification 34.9 → 31.2 ms in the parse bench; in the
     tallies 46.1 → 43.3 ms. With the discard check, about −5 ms per 100k
     records (−10%). *Exactness:* the same results by the arguments given;
     the prototype's tallies dump equals the original's on every input
     tried.
4. **Read samples on several threads, and merge the tallies.** For a
   top-level array, split the file at element boundaries. Finding them
   needs a quote- and escape-aware pre-scan, as in simdjson's first stage.
   Then tally each part on its own thread, and merge the trees in order
   with `Tallies::merge`. That is exact by construction: a merged tree
   equals the tree of reading on, and the unit test
   `merging_trees_is_reading_on` checks it. A part that fails is read
   again sequentially from the start, so that the first error in document
   order is reported, as stream-json reports it.
   - *Gain (estimate, not prototyped):* reading is 97% of a large run and
     splits well, so on 8 performance cores the wall time of the 267 MB
     file could fall 4–6×. CPU time would grow slightly.
   - *Cost:* the most complex item here. It needs the whole file
     (`mmap`, or reading ahead) instead of a 64 KiB window, so it suits
     regular files, not standard input. The WebAssembly engine is single
     threaded.
5. **Count repeated cases without hashing.** Keep the last case id per
   place in `add_case`, and compare the bytes before hashing (here
   `"ruling"` 100,000 times; `"wotc"` and `"scryfall"`).
   - *Gain (estimate):* `add_case` is 7.4%, `intern_text` 2.7% of it; about
     −1 to −2 ms per 100k records.
   - *Exactness:* the same id, so the same counts.
6. **Build the pluralize rules at compile time.** *Done; see
   [Status](#status).* Serialize the
   `regex-automata` multi-pattern DFA in `build.rs`, as the Markov chain
   already is, and deserialize it at run time.
   - *Gain:* −0.7 ms and −12,600 allocations per process. That is 1.5% of
     this run, but about 15% of a small one.
   - *Exactness:* the same patterns. The searcher only selects which
     rules to try.
7. **A cheaper window.** Read straight into the window's buffer and
   validate in place, or memory-map regular files and use the in-memory
   tokenizer.
   - *Gain:* up to the 2.2 ms that remain between reading from the file
     and from memory, after item 3. `read` itself (2.8 ms for the whole
     file) stays.
   - *Exactness:* decoding must stay Node's `StringDecoder` for invalid
     UTF-8. Valid input is borrowed as is.
   - *Not worth it:* larger read chunks (64 KiB → 1 MiB) gained nothing.
8. **Key tallying in the `JSON.parse` reader** (the WebAssembly engine's
   path): map the reader's key-table id straight to the key's index in the
   object tally of a place, caching the last one, instead of comparing
   texts. Its tallies path is 7 ms slower than its `CompressedJSON` path
   (38.6 against 31.6 ms). Items 2, 3 (the classifier), 5 and 6 apply to
   that engine too. Items 1 and 7 do not: that reader already scans by
   word.

Items 1 to 3 are small, local changes, and together they make the CLI
1.6–1.7× faster on this input. Existing tests cover them. The differential
harness compares the tally path with the reference path, so it checks
what only the tallies do: items 2 and 3's UTF-16 bound. The tokenizer and
the classifier are shared by both paths, so the harness cannot see a bug
there; the tokenizer's chunking unit tests, `cargo xtask parity` and
`cargo xtask diff` against the TypeScript CLI can. Item 4 is the one that
changes the scaling for large files.

How it differs from the prototypes:

- Item 1's scan is shared by both readers (`input::json_scan`). The
  `JSON.parse` reader now also takes the first stop from the mask's
  lowest set bit, where it went on byte by byte from the start of that
  word.
- Item 3b asks the recognizer whether a UUID can be a date, time or
  date-time to it (`DateTimeRecognizer::rejects_uuids`, `false` by
  default, `true` for the three built-in recognizers: the default one,
  Kotlin's and Swift's), and tests only strings of 36 bytes.
- Item 6's build script also translates the rules, and builds minimized
  dense DFAs, which load in 30–37 µs per rule list: a process does no
  other rule work. Sparse DFAs would be 22% smaller but take 360–450 µs
  to load. The WebAssembly module uses them too: it grows by 181 KB,
  18 KB gzipped (see
  [BENCHMARKS.md](BENCHMARKS.md#reading-after-the-cli-profile)). A hash
  of the rule tables the build script read is checked against the
  crate's own tables when the crate compiles.

Exactness of what is implemented:

- The whole CLI against main gave byte-identical stdout, stderr and exit
  code on 20,484 runs, 425 of them failing identically, with the 9
  option sets of the prototypes: the files of `tests/inputs/json`, the
  edge cases below, 40 more for the word scan (every escape, stop and
  multi-byte character at offsets 0 to 17 from a quote, stops around
  every offset of three 64 KiB chunks, raw control characters and invalid
  UTF-8 at and around chunk boundaries, a string unterminated at a
  boundary), the 100k and 1M files, the text-heavy and pretty-printed
  inputs, and the 2,000 generated documents.
- `cargo xtask streaming-fuzz --path all` on 1,000,000 seeds found no
  difference (6,000,000 graphs, 299,769 whole runs, 24,405 failing
  alike). The harness cannot see the tokenizer and the classifier, which
  both paths share; unit tests do. The word scan is checked against the
  byte-wise one with every byte value at every position of a word (among
  plain bytes next to the stops' values and of 0x80 and above), every
  stop at every offset from every start, a byte of every value after the
  first stop, and random bytes; and in the tokenizer, with a stop, escape
  or multi-byte character at every offset modulo 8 from the quote, read
  whole and in chunks of 1 to 17 bytes. The UUID-first classifier is
  compared with the recognizer-first order on 50,000 strings of 36
  characters, under each built-in recognizer. Pluralize's DFAs select
  exactly the rules whose own regex matches, on 31,586 words.
- `cargo xtask parity`: 11,177 of 11,177. The fuzz targets `json_stream`
  and `json_parse` ran 5 minutes each (1.8 million inputs each) without a
  finding. npm/quicktype-core's tests, its differential suite (19,078
  scenarios, 0 different) and its browser smoke test pass.

### Exactness of the prototypes

- The tally tree of the prototypes (items 1 and 3) is the same as
  without them, compared as a dump of every node, case and count. This
  held on all 220 files in `tests/inputs/json`, both generated files and a
  29.9 MB Python-written variant of the input.
- The whole CLI, with all three prototypes on against off, gave
  byte-identical stdout, stderr and exit code on 2,088 runs. Those were
  232 files (`tests/inputs/json`, the 100k file, and edge cases: escapes
  that straddle 64 KiB chunk boundaries, 70 KB strings, URIs after an
  unrestricted string, `$ref`, a control character, an unterminated
  string, a bad escape) times 9 option sets: `-l ts`, `-l rust`,
  `-l go --no-enums`, `-l kotlin --all-properties-optional`,
  `-l swift --no-ignore-json-refs`, `-l cs --no-maps`,
  `-l python --no-date-times`, `-l schema` and
  `-l java --no-uuids --no-integer-strings`. 27 runs failed identically.
- The same comparison on 2,000 documents from the differential harness's
  generator (`cargo xtask streaming-fuzz --dump`) gave 18,000 identical
  runs, 254 of them failing identically, and no difference. That covers
  enum pools at the thresholds, dates, UUIDs, URIs, strings around 64
  units, `__proto__`, `$ref`, maps around 500 keys, deep nesting and broken
  samples, with the same 9 option sets.
- The differential harness with prototype 2 in the tally path found no
  difference between the tallies' graphs and the reference path's in
  220,000 seeds: 440,000 graphs and 21,978 whole runs, 1,781 of which
  failed alike. A deliberately wrong variant was caught within 20,000
  seeds: it also skipped strings that could be URIs.

## Reproducing

```sh
node -e 'import("./npm/quicktype-core/test/bench/generate.mjs").then(({generateRulings}) =>
  require("fs").writeFileSync("rulings-100k.json", generateRulings(100000)))'
cargo build --profile profiling -p quickertype
target/profiling/quicktype rulings-100k.json -l ts -o out.ts --debug print-times
QUICKTYPE_INFERENCE=compressed-json target/profiling/quicktype rulings-100k.json -l ts -o out.ts
samply record -r 4000 --iteration-count 40 --unstable-presymbolicate \
  target/profiling/quicktype rulings-100k.json -l ts -o out.ts
node ../quicktype/dist/index.js rulings-100k.json -l ts -o out.ts --debug print-times
```

`generateRulings(1000000)` makes the 267 MB file; it needs Node's
`--max-old-space-size=8000`. The phase instrumentation, the parse bench
and the prototypes are not in the repository. Each is small enough to
redo from its description above. The phase instrumentation is a counting
`GlobalAlloc` over mimalloc, plus marks in `make_quicktype_options`, in
`onTiming` and after writing.
